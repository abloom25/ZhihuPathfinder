## 同伴接入方式

优先把修复补丁合入现有仓库，保留同伴自己的样式修改；完整源码是对应修复基线的备选。合并冲突重点查看 App.jsx、SavedScreen.jsx、ShareReceive.jsx。不要只复制 JSX，必须一起接入 shares.js、flow.js、依赖锁和新增测试。

Node 22，pnpm 10。在源码根目录执行：

```sh
pnpm install --frozen-lockfile
npm test
npm --prefix frontend run build
AUDIT_RESULTS=audit/recheck-results node audit/run.mjs
npm --prefix frontend audit
```

现有后端测试会更新 `backend/test/content-quality-verification.json` 和 `contract-verification.json` 的验证时间；这是测试产物，不是业务变更。重复测试使用新的 AUDIT_RESULTS 目录保留既有证据。

前端本地开发仍为 `pnpm dev`，Vite 的 `/api` 代理目标仍是 `127.0.0.1:18787`。正式站点需要静态资源、同源 API 反代和 SPA fallback（包含 `/share/:id` 与 `/?record=...`），不要把 Vite 开发服务器公开。分享文件继续采用单实例、持久磁盘；不要无协调地运行多个写入进程。

接收页新增的“保存我的记录与关联”直接使用既有本地记录能力，不增加后端接口。保存自己的记录不等于公开；公开仍需预览、明确勾选同意和确认。

## 复做浏览器故障验收

先构建，然后只在本地运行：

```sh
AUDIT_RESULTS=audit/recheck-results AUDIT_UI_PORT=18111 AUDIT_API_PORT=18112 node audit/serve.mjs
```

1. 用新的浏览器 origin 或测试配置打开页面，首次点“我的问津”，应显示空态。
2. 完成一轮选择 → 揭晓 → 预览 → 保存，填写明确的演示文字。记下私有记录数量。
3. 打开分享、填写处境、预览。另一个终端执行 `touch audit/drop-next-share`，再勾选公开同意并提交。
4. 应显示“未能确认请求结果”，不要出现“还没有创建”。GET `/api/v1/shares` 此时恰好有一条本次内容。
5. 刷新、从原记录重开分享，内容冻结且为原提交。勾选确认后重试：服务端同一个 ID 返回 200，数量不增加。
6. 完成并关闭，再刷新重进，仍能管理原分享。接收页也有同设备撤回入口。
7. 接收页写一条自己的记录并保存。详情必须分开展示自己的原话、关联分享副本和来源链接；刷新后不丢。
8. 从原分享管理入口撤回。接收链接应 404，自己的记录与保存的来源副本仍在；不要将其重新自动公开。
9. 将 `audit/fixtures/bad-draft.html` 复制到 `frontend/dist/audit-bad-draft.html`，仅在测试标签访问该路径，再点“回到我的问津”。应能查看和导出原记录；返回探索仍提示草稿损坏，直到明确开始新一轮。
10. 使用合成夹具分别验证 demo=true 与 false。所有夹具应注明测试身份，不把 false 冒充真人材料。

这些脚本没有无限递归或无限重试。新增参数需保留随机 seed 和最小失败用例，先复现再修改。没有真实知乎凭据时，搜索依赖测试采用隔离上游；正式凭据、HTTPS、手机/微信浏览器仍须由部署负责人在实际部署地址验收。
