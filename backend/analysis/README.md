# 单篇经历拆分：实现与首轮实测

这是离线分析模块，尚未接入现有 `/search`，不改变前端v0.1.0接口。运行依赖为已有开发依赖，Docker仍只包含稳定后端。模型是deepseek-v4-flash，读取环境变量DEEPSEEK_API_KEY；不打印、不保存密钥。

## 已实现的三步

1. `generate(item)`输入单篇API片段，模型输出事情、时间、行动、结果及逐项连续引文，并给出不同经历之间的边界依据。缺失项允许null；不确定和非亲历有独立状态。
2. `checkProposal(rawText, proposal)`检查JSON结构、引文存在、作者标记、拆分边界连通性、未知结果不带引文，以及明确愿望措辞。所有检查失败均拒绝该提案。
3. `presentation(...)`始终保留原文，永远不自动生成confirmedEpisodes。通过机械检查也只是review_required；uncertain不作确定拆分；失败返回原文。no_second_found不等于“确认只有一段”。

必须明确：程序不能独立证明自然语言含义。模型把他人标成author，或把旧结果引文放在新经历下面，可能通过字面检查。`test/split.test.mjs`特意构造了“旧offer套在新申请”的对抗例，证明机械检查会通过，但最终不会把它认证为确定经历。语义归属仍需对照原文核对；不得将机械通过显示成“核验通过”。

## 首轮真实调用结果

提示词与实现哈希在`protocol.json`中调用前冻结，原始输出、消耗tokens、耗时和错误在`results.json`。4例用于开发观察，另2例保留检查；材料此前可见，不是盲测。此次没有根据输出修改提示词再重算通过率。

| 材料 | 原关键词提示 | 模型与程序结果 | 原文核对 |
|---|---|---|---|
| H01-01 两份工作 | 漏提示 | 找到两段；机械检查通过 | 拆分有依据，但把“有想法…看情况…上班”的条件表述列为stated outcome，尚不宜确定展示 |
| H02-05 两年后再次求职 | 提示 | 拆分两段；引文不连续，被拦截 | 还错把2023.5.24绑定给后一次申请；不能因为日期字符存在就认可日期归属 |
| H02-10 第二次读题 | 误提示 | 将分析文字列为事件，subject uncertain，被拦截 | 应按非亲历建议处理 |
| H03-02 辞职倒计时 | 误提示 | 将同一倒计时不同日期拆成两段，空引文被拦截 | 还有语义过度拆分；拦截不是语义判断已正确 |
| H03-06 辞职建议（保留） | 无提示 | 描述为建议，但assessment和空episodes矛盾，被拦截 | 应为not_personal |
| H04-10 读研回顾（保留） | 无提示 | 返回uncertain，没有生成经历 | 保留原文，不能把弃答算成正确识别单一经历 |

最终：4例拒绝，1例不确定，1例待核对；没有输出可直接认证的自动拆分。调用约1.1–9.1秒/例，仅这次样本，不代表延迟保障；token计数见原始usage，不换算未经核实的账单金额。

## 如何运行

在工程根目录：

```sh
npm ci
npm test
```

19组测试通过，其中6组新增测试覆盖拆分、引文、作者、边界、愿望、结构错误、旧结局误归属和接口不可用回退。默认测试不调用付费模型。

`node analysis/run.mjs`会调用6次真实模型并重写protocol/results；重跑前归档已有结果。只传已保存的公开材料，未输入私人记录；无需知乎再次检索或招募测试者。

## 当前决定与后续

保持现有候选原文展示，不把该模块接到自动展示路径。新模块作为可运行的分析实验和人工核对辅助。首轮未达到自动拆分可用门槛，不能说关键词问题已经完全解决。

下一轮应先用程序给原文片段编号，让模型引用原文编号而不是重抄长引文，并把“是否独立经历”和“是否已发生的结果”分开核对；语义错误仍须在独立保留材料上检查。不要通过放宽引文要求、把日期相邻视为归属证据来提高表面通过率。

API调用格式参考[DeepSeek JSON输出文档](https://api-docs.deepseek.com/guides/json_mode/)。JSON可解析不等于内容正确，本轮有直接证据。
